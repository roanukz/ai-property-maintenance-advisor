Product teardown

AI Property Maintenance Advisor

A short term rental owner is ninety miles from the property when the hot tub stops heating. They can describe the symptom and nothing else, so the technician drives out, looks at the panel, and drives back for the part. I built a tool that reads the equipment data plate from a photo, searches the documentation live, and hands the technician a brief where every claim carries a citation. The interesting part is what it does when it cannot find one.

The short version

Summary

  • The job is not diagnosis, it is packing the van. A technician who knows the model and the documented failure brings the part. One who knows only "it is not heating" brings a guess and sometimes a second visit.
  • Refusing to answer is the feature. A maintenance tool that invents a plausible repair is worse than no tool, because the cost of a confident wrong answer lands on someone standing in front of live equipment. The tool has a NO RELIABLE ANSWER state, and it is enforced in code rather than requested in a prompt.
  • Every claim carries a citation and an honest label. Sources are tiered manufacturer, dealer, or forum, and a dealer page stays labeled dealer even when it is the best thing found. The label is only worth something if it is allowed to be unflattering.
  • I reviewed my own build adversarially before shipping and it found thirty one real defects, including one that would have failed intermittently on exactly the cases the product exists for.
  • It missed one of its own acceptance criteria and I published that rather than changing a setting to make the number. The setting that buys the speed is the setting that buys the refusal.
  • What it has not done is meet a technician. This is a validation instrument built to ask one question, and the question is still open.

Part 1

The problem

The property is an eight bedroom lake rental with a hot tub, two HVAC systems, a septic system, and a dock. The owner lives ninety miles away. When something breaks, the report arrives as a sentence from a guest or a cleaner: the hot tub is not heating, the upstairs is warm.

That sentence is everything the technician gets. It does not carry the model, the age of the unit, the code on the panel, or what was tried the last time this happened. So the first visit is often diagnostic rather than corrective, and the part comes on the second one.

The job: when equipment fails at a property I am not at, help me tell whoever is going to fix it what this thing is and what the documentation says about this symptom, so they arrive with the right part instead of finding out what they need.

Note the shape of that job. It is not "diagnose the fault." Nobody standing ninety miles away, and no tool, should be doing that. It is "carry the documentation to the person who can."

Part 2

What I actually know

I want to be careful here, because the honest version of this section is shorter than the flattering version.

Verified.

  • The operations tools in this category track the schedule, not the house. One of the leading products stores make, model, and serial as fields and does nothing further with them. The data is already being collected and is not being used.
  • Manufacturer error code tables for this equipment exist publicly and are findable. The Sundance 880 series documentation the tool retrieves is real, and so is the family match.
  • A competing tool in the adjacent workflow is free at one property and pays the cleaner. Anything that asks a vendor to do more work for no money is competing against that.

Inferred, and worth saying so.

  • That a cited brief reduces second visits. This is the thesis. It is not measured, and the whole build exists to test it.
  • That owners will photograph a data plate. It takes ten seconds, but nobody has been asked to do it yet.

Not known.

  • Whether a technician changes what they load in the van because a brief told them to. That is the question. One tradesperson answering it converts this from a build into a finding.

The demand signal I found while researching pointed somewhere slightly different from where I started: local forums are full of owners asking who to call, not what is wrong. Discovery, not dispatch. I noted it, kept building the narrower thing, and left the larger question open rather than quietly redefining the product to match the evidence I happened to find.

Part 3

The decision that shapes the rest

Every other decision in this build follows from one: the tool is allowed to say it does not know, and that is a success state, not an error.

The reasoning is about where the cost of being wrong lands. A search engine that returns a bad result wastes a few seconds. A maintenance tool that returns a confident, wrong, plausible looking repair instruction sends someone to open an equipment bay on live electrical, or to order a part that was never the problem. The asymmetry is not close.

So the product has a NO RELIABLE ANSWER state, and it is not a fallback for when things break. It is a first class output with its own layout, showing what was searched, what was found, and why that was not enough. In the demo you can trigger it deliberately, because a guarantee you cannot watch fail is not a guarantee.

A tool that is right most of the time and silent about which times is not a tool a technician can use.

Part 4

What I built

Photograph the plate, confirm what was read, get a brief. Two model calls and no database. The decisions worth defending are below.

Decision 1

The refusal lives in code, not in the prompt

Risk addressed: trust

I could have written "refuse when sources are insufficient" in the instructions and trusted it. Instead the response passes through validation that clears any candidates and any suggested steps when the state is NO RELIABLE ANSWER, whatever the model returned. Seventeen tests hold that behavior with no API key and no network, so the guarantee is testable on a laptop offline.

  • CostMore code, and a schema the model must satisfy exactly.
  • BoughtThe promise holds on a bad day, when the model is having one.
Decision 2

Label every source honestly, including when the honest label is weak

Risk addressed: trust, and usefulness

Sources are tiered manufacturer, dealer, or forum, and the rule is that a dealer blog stays labeled dealer even when it is the best source found. If everything located is forum content, the brief says so at the top rather than burying it. A reader who cannot tell an owner's manual from a stranger's guess is not better off for having both.

  • CostSome briefs look thinner than a tool that quietly promoted its sources.
  • BoughtThe label means something, so a technician can weigh it.
Decision 3

An observed code stops the search from widening

Risk addressed: usefulness

If the reported symptom includes a code visible on the panel, that code overrides symptom matching and the tool returns one confirmed candidate instead of a list. Same equipment, same model: the vague symptom returns six documented possibilities, and the observed code returns one. A list of six is research. One is a part number.

  • CostA misread code produces a confident single answer, so the brief tells the reader to confirm it on the unit.
  • BoughtThe difference between a technician researching and a technician packing.
Decision 4

Search at the moment of the question, instead of building a corpus first

Risk addressed: feasibility

The earlier design pre parsed manuals into a knowledge pack, and its own notes concluded that acquiring primary sources at scale was the open problem. That is a warehouse to build before answering a single question. Searching live at request time inverted it: the corpus becomes a byproduct of questions people actually asked, and every lookup is logged for exactly that purpose.

  • CostEach brief costs money and takes a minute or two, and quality depends on what is public.
  • BoughtA working product in a day instead of a data acquisition project with no end date.
Decision 5

Never diagnose. Carry documentation instead.

Risk addressed: safety, and liability

The brief never states a cause. It lists documented candidates, each with the documented meaning, the documented action, who should do it, and why it surfaced. Suggested first steps must be documented, safe for an untrained person, and actually actionable, which rules out "call a professional" as a step. Anything electrical or heat related is flagged and sorted to the top.

  • CostReads as less impressive than a tool that names the fault.
  • BoughtIt stays inside what the sources support, which is the only place it has any authority.

Part 5

What the run showed

Six acceptance cases, defined in the spec before the build. All six passed on content. One criterion did not.

CaseExpectedResult
Legible plateRead all four fieldsAll four, high confidence
Illegible plateReturn empty, not guessesModel, serial and date all empty
Hot tub, vague symptomCited candidates, filter and water level checksSix candidates, seven sources
Hot tub, code on panelOne confirmed candidate, not a listExactly one
HVAC, different categoryGrounded, or a clean partialGrounded, and invented no error codes for a category that does not display them
A model that does not existNO RELIABLE ANSWERRefused, with its search trail
Any brief, under sixty secondsUnder 60s57 to 117 seconds. Missed on three of four

The fabricated model case is the one I care about, and it passed for the right reason rather than by luck. The search established that the brand is real and has real manuals, that the model designation does not fit that brand's documented naming, and that generic troubleshooting advice for the brand was available. It declined to use it. Refusing when there is nothing to find is easy. Refusing when there is something adjacent and tempting is the actual behavior under test.

On the criterion I missed. Briefs took fifty seven to one hundred seventeen seconds against a sixty second target. One settings change would have made the number by reducing how much reasoning each brief gets. I did not make it, because that setting is also what buys the refusal behavior, and a brief that arrives in fifty seconds and occasionally invents a repair is a worse product than one that takes ninety and says it does not know. The honest record is that the criterion was wrong, or the product is too slow, and I have not yet earned the right to say which.

Part 6

What I would do next

  1. Put one brief in front of one technician and ask a single question: did this change what you would bring. Everything above is process quality. That question is the only one that turns it into evidence, and it needs one tradesperson and an afternoon.
  2. Settle what a tier label describes. Running it live surfaced a real ambiguity: a manufacturer's manual rehosted on a third party archive currently gets labeled manufacturer, because the document is genuinely the manufacturer's. But a reader scanning badges sees that label next to an unfamiliar host. Document origin or publisher identity, and I have to pick one.
  3. Measure the latency question properly rather than arguing it from principle. Run the suite at reduced reasoning and see whether the fabricated model case still refuses. If it does, the criterion was right and I was being precious. If it does not, I have a number that justifies the criterion being wrong.

Part 7

What I cut

The spec named these as out of scope before the build started, which is the only time a cut list is honest:

  • Accounts, and anything resembling a funnel. This is a validation instrument. Email capture would have told me nothing about the question.
  • Multi property, and integration with existing operations tools. Both are real, both are the business rather than the test.
  • Warranty deadline tracking and prevention scheduling. The most requested adjacent feature, and the one most likely to hide whether the core idea works.
  • The cleaner capture workflow. The right long term entry point, and a second unproven assumption stacked on the first.
  • A name and any branding. Deliberately unbranded during the test so nothing rode on presentation.

Appendix

Method made visible

Reviewing my own build adversarially

Before shipping I ran a structured review of the build against its own spec, across three independent lenses: does it match the specification, does it use the platform correctly, and what breaks. Every finding was then checked by a separate pass whose instruction was to refute it. Thirty five claims, thirty one confirmed, four refuted and dropped.

The four that mattered:

  • An intermittent failure on exactly the cases the product exists for. A long running search can pause and expect to be resumed. Unhandled, the request would fail after paying for every search, and only on the search heavy briefs, which are the real ones.
  • Output budgets that ignored how the model actually behaves and would have truncated a brief mid sentence.
  • A reassembly bug where citations split the response into pieces and rejoining them incorrectly corrupted the result.
  • A script injection hole in the shared brief, which is the file handed to a third party, and therefore the worst place in the system to have one.

I am including this because the review found things I would not have found by testing the happy path, and because the four refuted claims matter as much as the thirty one confirmed. A review that confirms everything it suspects is not reviewing.

What I got wrong

  • I pinned a dependency version from memory instead of checking, and the build failed on the first compile because the feature I needed did not exist in it.
  • I ran a production build while the dev server was running, which corrupted its cache and made every route fail until I cleared it.
  • One of my own tests was wrong. It asserted a string never appears, when that string legitimately appears in correctly escaped output. I checked the actual behavior in a browser before changing the assertion, because the tempting move is to edit the test until it goes green.

Honest limits of this write up

  • Zero real users. Every number here describes how carefully it was built, not whether it works for anyone.
  • The demo is recorded, not live, so you are seeing real output but not exercising the system.
  • The property, the owner, and the commercial detail are genericized. The equipment and the retrieved documentation are real and unaltered.
