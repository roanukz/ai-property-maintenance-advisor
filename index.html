Three minutes

Summary

  • The problem. An owner who lives far from a rental property hears about a broken hot tub or air conditioner as one sentence from a guest, and the technician's first visit often goes to finding out which part is needed (Part 1). The first version of this tool (v1) turned a photo of the equipment's data plate, the label with its make, model and serial number, into a brief cited to the maker's documents, and refused when the documents did not support an answer. But v1 remembered nothing: every brief paid for 7 to 8 fresh web searches, even for a unit it had researched before, and it knew nothing about the property (Part 3, Part 4).
  • The thesis. A tool that remembers what it has already verified, and knows each property's records, can answer a repeat question with fewer searches and for less money without giving up any of v1's guarantees, as long as those guarantees stay in code rather than in the instructions given to the model. That needed a program that can branch, loop, pause for a person and save its progress, which is what LangGraph (a library that runs an AI workflow as a graph of steps) provides; LangChain (a library of building blocks for AI apps) runs the research step inside it (Part 5). It also needed each step to go to the cheapest tool that can do it: Anthropic's Claude for reading the plate, choosing what to search and writing the brief, and Tavily, a web search service built for AI tools, on its free tier for search (Part 6).
  • The method. The bars were written into the product requirements on 17 September 2026, before any test ran: a repeat question about the same unit uses 2 searches or fewer, compared with the same unit's first v2 lookup; an invented model is refused 3 times out of 3 on the cheaper model; no cheap mode brief spends more than $0.15 and the whole build no more than $5; speed is reported, with no target. Replay (running the whole pipeline on recorded model replies and recorded search results, at no cost) tests the rules, the routing and the spending caps. Small live batches on Claude Haiku 4.5 and Tavily, run on 18 September 2026, test how the model behaves. A differential test sends 180 test briefs through both v1's validator (the code that checks each brief against the rules) and the rewrite's, and compares the verdicts (Part 8). Safety step flagging was tested later, on 29 and 30 September, against 345 steps labeled before any scoring, with the rule for choosing what ships written before any result (Part 9).
  • The results. The three live repeat questions used 0 searches (answered from memory), then 2 and 2 (short top ups, held to 2 by the top up limit itself), against 4, 4 and 5 on the same units' first v2 lookups: a pass on the bar of 2 or fewer. v1 ran 7 to 8 on every brief. The invented model was refused 3 of 3 times, each refusal made by the model, against a bar of 3 of 3. Briefs that needed research cost $0.0587 and $0.0632 and briefs answered from memory $0.0065 and $0.0082, against the $0.15 cap and an estimated $0.35 to $0.71 for a v1 brief. Briefs took 21.4 and 51.3 seconds with research and 4.8 and 5.2 seconds from memory, against 57 to 117 seconds for v1. A live run with synthetic property records attached cited the unit's earlier service record and its age. Offline, v1's and v2's validators agreed on all 180 test briefs (Part 8). A code check by Jev, a judgment model from TypeSafe, flagged 30 of the 31 safety steps in the half of the labeled set kept aside for the final score, against 20 for a rule matching the words breaker, power and heat, and on ten new live lookups every safety step was flagged, 14 of 14, the same as the writing model managed alone under its revised instruction (Part 9).
  • What it means. Remembering pays where it was designed to: an answer from memory cost about a seventh of a first lookup and took about a tenth of the time, though that repeat brief was thinner than the first. The saving comes from several changes made together (a model priced 5 times lower, search on a free tier, a lower search cap, and memory that can skip search), and the tests do not separate them. None of them loosens a rule, because every rule still runs in code. What the tests cannot show is that a cheaper brief is as good: the hot tub repeat from memory left out all 4 steps to try first that its first brief listed, and one live hot tub brief listed a step at the breaker without its safety flag, a finding about the model. A code check now flags such steps, though on the ten new live lookups the writing model, under a revised instruction that spells out which steps count, caught every safety step by itself; there is no clean figure from before that instruction to compare it with (Part 9).
  • Cautions, and how to check. Replay proves the rules, the routing, the spending caps and the page layout; it cannot prove how the model behaves. The live samples are small: three runs for the refusal test and three repeat questions for the memory test, and three refusals out of three is consistent with a true refusal rate as low as about 37%. Two of the three repeat passes were held to 2 searches by the top up limit itself; in both the model asked for more, and only the hot tub code repeat shows memory replacing search. The property records are synthetic, and no technician has used a brief yet. Every live v2 number here comes from a named run on one fixed build (a single frozen version of the code, identified by a fingerprint stored in every run record), with two exceptions from the safety check: its ten live lookups ran on the later build that added it, and its labeled set scores trace to a locked settings file and the Jev model version (jev-1.13.0), not to a build fingerprint. v1's come from its own live run of 18 August 2026, and the whole build spend also counts runs on an earlier build that was replaced. The safety step labels came from three model readers, not from people. The offline suite of 2,584 tests runs with the network blocked, no key and no cost (Appendix A).

Part 1

The problem

The property is an eight bedroom lake rental with a hot tub, two heating and air conditioning (HVAC) systems, a septic system, and a dock. The owner lives ninety miles away. When something breaks, the report arrives as a sentence from a guest or a cleaner: the hot tub is not heating, the upstairs is warm. That sentence is everything the technician gets. It does not carry the model, the age of the unit, the code on the panel, or what was tried the last time this happened. So the first visit is often diagnostic rather than corrective, and the part comes on the second one.

The job: when equipment fails at a property I am not at, help me tell whoever is going to fix it what this thing is and what the documentation says about this symptom, so they arrive with the right part instead of finding out what they need.

Note the shape of that job. It is not "diagnose the fault." Nobody standing ninety miles away, and no tool, should be doing that. It is "carry the documentation to the person who can."

Part 2

What I actually know

Verified.

  • The failure this addresses is an information failure. Aberdeen Group research, cited widely across field service writing, puts about 51 percent of repeat visits down to a missing or wrong part, against 25 percent for technician experience and 13 percent for a job scheduled too short. I am citing secondary sources quoting Aberdeen rather than the original report, which I could not reach. Source, second source.
  • The operations tools in this category track the schedule, not the house. One of the leading products stores make, model, and serial as fields and does nothing further with them.
  • Manufacturer error code tables for this equipment exist publicly and are findable. The Sundance 880 series documentation the tool retrieves is real.

Inferred, and worth saying so.

  • That a cited brief reduces second visits. This is the thesis, and it is not measured.
  • That owners will photograph a data plate. It takes ten seconds, but nobody has been asked to do it yet.

Not known.

  • Whether a technician changes what they load in the van because a brief told them to. One tradesperson answering that converts this from a build into a finding. Version two does not answer it either.

The demand signal I found pointed somewhere slightly different: local forums are full of owners asking who to call, not what is wrong. I noted it, kept building the narrower thing, and left the larger question open rather than quietly redefining the product to match the evidence I happened to find.

Part 3

What v1 proved

Every decision in both versions follows from one: the tool is allowed to say it does not know, and that is a success state, not an error. A maintenance tool that returns a confident, wrong, plausible looking repair instruction sends someone to open an equipment bay on live electrical, or to order a part that was never the problem. So the product has a NO RELIABLE ANSWER state, with its own layout showing what was searched, what was found, and why that was not enough.

A tool that is right most of the time and silent about which times is not a tool a technician can use.

v1 worked like this: photograph the plate, confirm what was read, get a brief. It made two calls to Claude Opus 5, the highest priced of the three Claude models priced in the build, using Anthropic's own built in web search capped at 8 searches, and kept no database. Five decisions shaped it, and all carry into v2.

Decision 1

The refusal lives in code, not in the prompt

Risk addressed: trust

Instead of writing "refuse when sources are insufficient" into the instructions and trusting it, validation code clears any candidates and suggested steps when the state is NO RELIABLE ANSWER, whatever the model returned.

  • CostMore code, and a schema (the exact shape the answer must have) that the model must satisfy exactly.
  • BoughtThe promise holds on a bad day, when the model is having one.
Decision 2

Label every source honestly, including when the honest label is weak

Risk addressed: trust, and usefulness

Sources are tiered manufacturer, dealer, or forum. A dealer page stays labeled dealer even when it is the best source found, and a brief built only on forum content says so at the top.

  • CostSome briefs look thinner than a tool that quietly promoted its sources.
  • BoughtThe label means something, so a technician can weigh it.
Decision 3

An observed code stops the search from widening

Risk addressed: usefulness

If the symptom includes a code visible on the panel, the code overrides symptom matching. On the same hot tub, the vague symptom returned six documented possibilities and the observed code returned one. A list of six is research. One is a part number.

  • CostA misread code produces a confident single answer, so the brief tells the reader to confirm it on the unit.
  • BoughtThe difference between a technician researching and a technician packing.
Decision 4

Search at the moment of the question, instead of building a corpus first

Risk addressed: feasibility

An earlier design parsed manuals into a knowledge pack in advance, and acquiring primary sources at scale was its open problem. Searching live at request time inverted that: the corpus would become a byproduct of questions people actually asked.

  • CostEach brief costs money and time, and quality depends on what is public.
  • BoughtA working, testable product instead of a data acquisition project with no end date.
Decision 5

Never diagnose. Carry documentation instead.

Risk addressed: safety, and liability

The brief never states a cause. It lists documented candidates, each with the documented meaning, the documented action, who should do it, and why it surfaced. First steps must be documented, safe for an untrained person, and actionable. Anything electrical or heat related is flagged and sorted to the top.

  • CostReads as less impressive than a tool that names the fault.
  • BoughtIt stays inside what the sources support, which is the only place it has any authority.

Part 4

Where v1 stopped

Running v1 showed three limits that no prompt could fix, because each is about what the tool remembers and knows, not about how well the model writes.

  • It forgot everything. Every brief ran 7 to 8 live searches and read 42,000 to 91,000 tokens of input (a token is a word fragment, the unit models are billed in). A second question about the same hot tub paid the full price again. v1 logged every lookup but never stored what it verified.
  • It knew nothing about the property. The brief has a "this has happened before" field. It was empty in all 4 recorded v1 briefs, because v1 had no service history to fill it from.
  • It had no path for aging equipment. When a part is discontinued, the useful answer is a documented successor model, and v1 had nowhere to put one.

Cost made the first limit sharper. v1 never computed its own cost; its logged usage, priced at current list prices, puts a v1 brief at an estimated $0.35 to $0.71 (Part 6). Version two sets out to remember what it has verified, to know each property, and to spend less per brief, without moving any of the five decisions above out of code. Two items from v1's cut list come back for that reason: several properties, and warranty tracking.

Part 5

Why LangGraph and LangChain

LangGraph is a library that runs an AI workflow as a graph of steps. Each step reads and writes a shared record of the run, and arrows between the steps, called edges, decide what runs next. LangChain is a library of building blocks for AI apps: connectors to model providers, tools, and a ready made agent loop in which the model calls a tool, reads the result, and decides what to do next.

v1 was a fixed sequence of steps, and plain code was the right tool for it. v2 adds four things a fixed sequence cannot express cleanly: routing (answer from memory, top up with a few searches, or research in full), a bounded retry loop, a pause for a person to confirm the unit, and saved state for each property. Those four are a real reason to use a graph runtime, not a way to show off a framework.

The split: LangGraph runs the flow, LangChain runs one step

LangChain's ready made agent, create_agent, was considered for the whole flow and rejected: it cannot hold a confirmation pause that survives the program being closed and started again, the validation retry loop, or state kept per property. So LangGraph runs the whole flow, and create_agent runs only the research step inside it, where a model and tool loop is exactly what is needed.

What each capability is, and what the owner or technician gets from it
CapabilityWhat it meansWhat the user gets
Interrupt and checkpoint (LangGraph) An interrupt is a deliberate pause that waits for a person's answer. A checkpoint is a saved snapshot of the run, written after each step to a small database file. The owner checks the unit and the code before anything is spent on research, and can finish later, even after a restart, without paying for the plate reading twice.
Conditional edges (LangGraph) Arrows whose destination is chosen by a small function. The tool answers what it already knows and searches only when it has to. A failed check gets one smaller second pass, only if the budget allows.
Parallel branches and typed state (LangGraph) Several steps run at once, and the run's record has a fixed shape with a merge rule for each value they write. Service history, stored facts and live research are gathered together, and the cost and the "what was searched" list on each brief include every call.
create_agent and middleware (LangChain) The ready made loop of model and tools, and code that wraps every call in it and can stop a call before it happens. A known worst case for each lookup: at most 5 searches and 3 page fetches on the first pass, and 2 more searches on the one smaller retry (v1 allowed 8 searches), and no model call once the money is gone.
Structured output (LangChain) The model answers in a fixed, typed form, like filling in a form, not in free text. Every citation in a brief points to a page the tool actually retrieved, because the model can refer to a source only by its number and code builds the list.
Provider connectors (LangChain) Ready made connections to Claude and to Tavily's search and fetch. Search runs on a free tier while Claude does only the judgment, so the owner pays for one model at its cheapest adequate setting, and the recorded demo shows exactly the calls that were made live.

The tradeoffs actually paid

  • The names move fast. Many functions were renamed or moved after the 1.0 releases, and the documentation and the source code disagree in three places. Every name was checked against the current release, the source was taken as correct, and v2 relies on none of the three disputed behaviors.
  • No stock fake model could drive the agent. A fake model returns scripted replies so tests cost nothing. None of LangChain's supports tool calling (the model asking the code to run a search or fetch), and one silently loops back to the start of its script. v2 wrote its own, which fails loudly. Because it never checks the form the way the real API does, one paid check covered that gap.
  • The structured output ceiling. Anthropic limits a form to 24 optional and 16 either or fields, and LangChain passes the form through unchanged. A draft modeled on v1's lenient form would have failed on the first paid call, so the form is now flat, with every field required.
  • Defaults that had to be overridden. The agent's loop limit defaults to 9,999 steps, so the middleware caps are the only real guard; LangChain's own search limit leaves no reason in the run's record, so v2 wrote two small middleware pieces of its own. The Claude connector defaults to the model's maximum output, which on Haiku would reserve $0.32 against a $0.15 cap, and neither connector has a timeout until one is set.
  • A rewrite in a second language. v1 is TypeScript and v2 is Python, because Python has the more complete LangGraph ecosystem (an inference, not a measurement). The price was porting v1's validator; the differential test pays it back (Part 8).
  • Model lifetime. Haiku 4.5 retires no sooner than 15 October 2026, and the live command refuses Haiku runs from that date until the model list is rechecked. A Sonnet 5 fallback would cost about 2.6 times as much, an estimate.

Alternatives rejected

  • A vector store beside the graph. It finds text by similarity of meaning. In my earlier project on documentation gaps, vector search scored 24 correct against 23 for graph retrieval, a gap too small to justify a third way to look things up.
  • A hosted graph database. At the size this build was planned for (about 50 nodes, an estimate), a Python library that holds the graph in memory and saves it as a plain file does the same job, with no account and nothing to pay.
  • Building the corpus up front. v1 already rejected it. v2 grows memory only from lookups that really happened, so early questions pay for full research.

Part 6

Two APIs, each for its job

An API is a service the code calls over the internet and pays for by use. v1 used one API for everything: Claude Opus 5 read the plate, ran Anthropic's own web search, and wrote the brief. v2 splits the work by what each step actually needs. Since 30 September a third service, TypeSafe's Jev, also checks each step to try first in a brief for safety (Part 9).

Claude, for judgment

  • Reads the plate photo.
  • Decides what to search and which pages to fetch.
  • Classifies a vague symptom, only when the routing rules cannot decide.
  • Writes the brief.
  • Cheap mode, the one run live, uses Haiku 4.5, the lowest priced of the three models priced in the build, for every step. Full mode hands only the writing to Sonnet 5, at about $0.09 more per brief (estimate); it is tested in replay only.

Tavily, for finding pages

  • Runs the web searches and fetches page text.
  • Free tier: 1,000 credits a month. A basic search costs 1 credit; the 2 credit advanced search is switched off.
  • A page fetch costs 1 credit per 5 successful pages; failed fetches are free.
  • Paid overage is switched off, so a search costs $0.

Why the split is cheaper

Per million tokens, Haiku 4.5 costs $1 in and $5 out, Sonnet 5 costs $2 and $10, and Opus 5 costs $5 and $25; Anthropic's server search adds $0.01 per search. So the model price alone is 5 times lower on Haiku, and the search line, an estimated $0.07 to $0.08 per v1 brief (7 to 8 searches at $0.01), falls to $0 on Tavily's free tier. The $0 holds only on the free tier: at Tavily's pay as you go rate of $0.008 a credit, a worst case first pass of 8 credits would cost about $0.064 (arithmetic, not measured). So at volume most of the saving comes from the model and from memory skipping search.

The second payoff: the rules stay in code

In v1, Anthropic's built in search returned its citations in a way that did not work together with structured output, so v1 could not have code build the source list; it relied on an instruction to the model not to pad the bibliography. In v2, the search and fetch wrappers hand code the raw results. Code builds the source list only from searches and fetches that actually succeeded, the model can point to a source only by its number, and because code holds the raw page text it can check that every quote appears word for word on its page and that a cited error code appears there as a whole word. The instruction became a rule enforced in code.

How LangChain and LangGraph carry the split

  • LangChain puts both providers in one loop. The agent runs Claude's tool calling over Tavily's search and fetch, and one configuration file names the model for each step.
  • Middleware counts both bills in one place. It counts Tavily searches and fetches against their limits and reserves each Claude call in a spending ledger before the call is made.
  • LangGraph decides whether either API is called at all. Routing skips search when memory holds enough verified facts and sends a top up of 2 searches when it holds some. The confirmation pause sits before any research spend, so the only paid call before the owner confirms is the plate reading, which cost $0.0028 and $0.0029 live.

The tradeoffs. Citation mapping, the page evidence checks and the credit count all became v2's own code, which is more to maintain than one provider, and it is the part that keeps the source list honest. The second tradeoff is quality: Haiku was picked because it is cheapest, and a cheaper model can write a less complete brief while every rule passes. So "cheaper" and "as good" are separate claims, and this page supports only the first (Part 9).

Part 7

What v2 lets owners and technicians do

Each feature is described by what the person gets and why it matters on the day something breaks. Where a live run shows it working, the demo case that replays it is named; the recorded v2 demo replays those runs.

Feature 1

Remember equipment it has already researched

For: the owner paying for the lookup, and the technician waiting on it

v2 keeps a knowledge graph: facts stored as things and the links between them, such as "this model shows this code", "this model has this documented cause", "this model replaced that one". Every fact carries its page address, the date it was retrieved, and the exact sentence from the page that supports it, and is stored only from a validated brief on a live run.

Live, a repeat of the hot tub's FLO code question (FLO is the panel's flow switch code) was answered from memory with no search, for $0.0082 in 5.2 seconds, against $0.0587 and 51.3 seconds for its first lookup (demo cases 1 and 2). The repeat brief was thinner, though: it gave the code and its documented meaning but none of the 4 steps to try first that the first brief listed, and it named a technician rather than anyone as the person to act.

The air conditioner's first lookup stored 3 documented causes. A new question about it, a fan that would not spin, checked those first, but the symptom check could not match any of them, so the run was held to a short top up of 2 searches and the brief used none of the stored causes: $0.0217 in 15.5 seconds, against $0.0632 and 21.4 seconds (demo cases 4 and 5). That saving came from the smaller top up limit, not from reused facts.

  • GetsA repeat question about the same unit skips or shortens search, so it is faster and cheaper, though an answer from memory alone can be thinner.
  • WhyRental properties see the same equipment fail again, and v1 paid full price every time.
Feature 2

Know the property: history, age and warranty

For: the technician, before the visit

A matching earlier service record fills "this has happened before", cited to that record; a record for a different appliance is thrown out. Code computes the unit's age from the install date in the records, and the model is told not to. Warranty terms are quoted only from the property records, with the record number.

Shown live, on synthetic records. A live run on the hot tub with seeded synthetic property records attached (the model and the documentation were real; the records were made up for testing and are labeled so) cited the earlier service record ("Panel showed FLO and heater would not run; cleared after filter cleaning and water level top-up"), stated the unit was installed on 10 June 2021 and about 5 years old, and quoted the record's warranty terms, which say they are synthetic. It used 0 searches and cost $0.0065 in 4.8 seconds (run t-550f902f22f846d5, demo case 8).

  • GetsWhat was tried last time, how old the unit is, and whether it is under warranty, on one page.
  • WhyThat is the context the one sentence report from a guest never carries.
Feature 3

A confirmation pause before any money is spent

For: the owner

After the plate is read, the run pauses. The owner confirms or corrects the model and the code. If the model number is unreadable, the run stays paused until someone types it, so a guess is never treated as confirmed. Live, the clear plate was read exactly, every field at high confidence, and the blurry plate came back with every field, model, serial and date included, marked unreadable rather than guessed (demo case 7).

  • GetsA check on what was read, before the lookup is paid for.
  • WhyA wrong model or a misread code wastes the whole lookup and can point to the wrong part.
Feature 4

Spending capped in code, and reported honestly

For: the owner paying the bill

Every paid call is reserved in a ledger (a running record of spend) before it is made, so a cheap mode brief stops at its $0.15 cap, give or take one call's estimate error. The ledger is never deleted, so a reset cannot grant a fresh budget. Running out of money is its own "budget stopped" status and never counts as NO RELIABLE ANSWER, because an empty wallet is not a finding about the documentation.

  • GetsA known worst case per brief.
  • WhyA tool that can run up an open bill is not one an owner leaves running.
Feature 5

The refusal and the honest labels, kept

For: the technician deciding what to trust

NO RELIABLE ANSWER is still enforced in validation code, and code can lower a source's tier label but never raise one. The badge now names the website that hosted the document beside it, so a maker's manual found on a third party archive is not a surprise. Live, the invented model was refused on all 3 runs, each time by the model itself after it had reached the brand's real documentation (demo case 6).

  • GetsThe same guarantees as v1, plus the host behind every badge.
  • WhyCheaper is only useful if the brief is still safe to act on.
Feature 6

Upgrade options and maintenance, cited or absent

For: the owner deciding whether to repair, and planning prevention

A successor model appears only when a fetched page names it as a whole word ("Optima 880" is not taken from "Optima 880X"), and a price only when the cited page states that exact amount. A maintenance interval is kept only from the manufacturer, and code computes the due date from the property's maintenance log. Upgrade options are tested in replay only; no live run needed one. Live, the air conditioner's second brief quoted two maintenance intervals from Trane's own pages, and with no property records attached it left the due date uncomputed rather than guess.

  • GetsA cited path to a replacement when parts run out, and a due date from the maker's own interval.
  • WhyA guessed successor sends someone shopping for the wrong unit.
Feature 7

A brief a technician opens with no app

For: the technician

The brief is a single self contained page. Nothing loads from anywhere else, and all model text is escaped so it cannot run as code.

  • GetsA file to text or email, with no login.
  • WhyThe person who needs the brief is not the person who has the tool.

Part 8

How v2 was tested

Replay runs the whole pipeline on recorded model replies and recorded search results, at no cost and with the network blocked. It proves the rules, the routing, the ledger and the page renderer, but not how the model behaves. Small live batches on Claude Haiku 4.5 and Tavily, run on 18 September 2026 on one fixed build, test the model. The bars were written into the requirements on 17 September 2026, before any test ran.

The rules stayed in code

  • 14 of v1's 17 guardrail behaviors are ported. The other 3 tested parsing a block of text the model returned, which structured output removed, and are marked obsolete.
  • v1's and v2's validators agree on the decision, the reason and the cleaned brief for all 180 differential test briefs: 16 from v1's guardrail tests and 164 new edge cases. The test needs v1's private source, so it skips on a fresh copy of the repository.
  • A refusal or a budget stop clears candidates, steps, upgrade options and maintenance items; tier labels can be lowered by code, never raised; an observed code still narrows the answer.
  • A stored fact needs a word for word evidence sentence from its page; a fact that fails is dropped, not downgraded.
  • The offline suite of 2,584 tests runs with the network blocked, and all 1,105 planted bugs are caught. A planted bug is a deliberate small break in the code, used to check that the tests notice it.

Part 9

Design decisions, and one finding about the model

Four design choices shape how memory and replay behave. Each is there for a reason an owner or a technician would recognize. How they came about is recorded in the project's decision log (DECISION-LOG.md in the source).

Decision 6

Store documented causes as well as codes

For: owners of equipment that shows no codes

An air conditioner rarely displays an error code; what its documentation lists is causes, such as a blocked outdoor coil or low refrigerant. So memory keeps a documented cause, with its documented action, under the same word for word evidence rule as a code, and a cause label must share at least 2 content words with its quote. Live, the air conditioner's first lookup stored 3 documented causes and dropped a fourth whose quote was not on its page. The next question about the unit, a fan that would not spin, matched none of the 3, so they only sent it to a 2 search top up, and all 3 causes in that brief came from search.

Decision 7

Never answer a question with no confirmed code from stored codes alone

For: the technician, who needs the full list when there is no code

"Not heating" can have several documented causes. Answering it from the one code memory happens to hold would narrow the list to a single part the symptom never pointed to. Answering from memory alone needs at least 3 distinct verified causes and a match from the symptom classifier; anything less gets a top up of 2 searches. Live, the vague hot tub question found no stored causes, so it topped up with 2 searches. The brief still listed only 1 documented possibility, the stored FLO code, left unconfirmed, where v1 listed six for the same symptom: the top up added a source but no other cause, and its limit blocked 2 more searches and 2 fetches.

Decision 8

Whole word excerpts

For: anyone reading a quote in a brief

Excerpts of a page start and end on word boundaries. A quote cut in the middle of a word can change its meaning, as "$12" cut from "$129" would, and cannot be checked word for word.

Decision 9

Live recordings are replayable offline

For: checking the results

Replay reads the real page text saved from a live run, and marks grounding "unverifiable" when that text was not saved. On the build machine, every live run can be rerun offline for free, and the recorded demo replays the live runs verbatim. The live recordings stay on that machine, out of the public repository, so a reader can check each run ID and build fingerprint in the demo's data file but cannot yet rerun them.

A finding about the model: a step at the breaker without its safety flag

On that build, the instructions asked the model to flag any electrical or heat related step as a safety step, and code sorts flagged steps to the top. On the fixed build, the hot tub's first lookup (run t-267045726dd04118) listed "Turn off power at the breaker, wait 20 minutes, then restore power" as its fourth step with no safety flag. The air conditioner's second question did flag its breaker step, so the model does it sometimes, not always.

Code could not fix this on its own terms. It can reorder the steps the model flagged, but deciding what counts as a safety step means either trusting a judgment or writing a rule that judges the step's wording, and every step must come from a cited source, so code cannot add one. I reported it as a finding about Haiku on that build, not a code failure, and made testing a fix the first item in Part 10.

The fix, tested before it shipped: a safety check in code

On 29 and 30 September I tested three ways to catch such a step, each able to add a safety flag but never remove one or add a step: a word rule that flags any step naming certain words (the published list was breaker, power and heat; a tuned list, chosen on the tune half described below, drops the bare word heat but keeps heater and heating, and adds wire, panel, door, disconnect, electrical, jumper and box); Jev, a judgment model from TypeSafe that reads each step and answers how likely it is to be a safety step, as a probability from 0 to 1; and Jev together with the tuned word rule. The test set was 345 steps, taken from maker and dealer documentation and from the tool's own earlier briefs, and labeled before anything was scored by three model readers working blind, who agreed on 338 of them. The set was split into a tune half, where each check's settings were chosen, and a held out half of 175 steps, 31 of them safety steps, which no setting ever saw. The settings were locked in a file before the held out half was scored, once, and the rule for choosing what ships was written before any result: of the tuned word rule, Jev, and Jev together with the tuned word rule, drop any whose precision (the share of its flags that were real safety steps) is below 0.60, then take the highest recall (the share of real safety steps it flagged), then the higher precision. Separately, on 29 September, before the live check, the instruction to the writing model was revised to spell out which steps count as safety steps: power or gas switched off, on or reset; working near anything that can be live, hot or carrying gas; and running or testing a heater.

The held out half has no steps the tool wrote, so the writing model's own flags are not in this table; the ten live lookups below measure the writing model. With 31 safety steps the sample is modest. A 95% interval is the range the true rate probably falls in, given how few steps were tested. In those intervals, Jev's recall (0.838 to 0.994) sits clear of the published word rule's (0.469 to 0.789) and barely overlaps the top of the tuned rule's (0.534 to 0.839), and the precision intervals of all four checks overlap. The tuned word rule plus Jev flags every step Jev flags; its extra flags caught no safety step Jev missed, which is why its precision is lower.

What shipped, and the live check. Jev and the tuned word rule plus Jev tied on recall, and Jev alone had the higher precision, so Jev ships, flagging a step when it answers 0.51 or higher; the published breaker step scores 0.98. Then ten new first lookups ran live on the build that added the check, five with the hot tub's FLO question and five with the air conditioner's fan question. Their briefs held 31 steps, 14 of them safety steps by the same three readers, and all 14 were flagged. The writing model, under a revised instruction that spells out which steps count, flagged all 14 by itself; Jev flagged the same 14 and added two false flags on fan blade steps, so on these runs it caught nothing the writer missed. The tuned word rule, which is not shipped, also flagged all 14, with 2 false flags on other steps (14 of 16). There is no clean figure for the writer before the revised instruction: most of the safety steps in the 18 September briefs that would give one came from the build that was replaced, so that comparison is held back. The safety step work cost $0.4878 in all, most of it the ten live lookups.

What these numbers cannot say. The labels came from three model readers, not from people. The tuned word list did not hold up: it scored precision 0.955 on the half it was tuned on and 0.647 on the held out half, below the published list, because words such as "door" and "box" found harmless steps in pages it had not seen. The live check is small, 14 safety steps from two questions, mostly at a breaker, and the revised instruction alone caught all of them, so the held out half is the stronger evidence for the check itself. With Jev alone shipped, a failed check falls back to the writer's own flags and one line in the brief telling the reader to treat any step at a breaker, a panel, a heater or a gas valve as a safety step, not to the word rule; whether it should is an open question. The recorded demo still shows build 839b1854a0aaf25e from 18 September, so its briefs carry the writer's flags only.

Rules that stand

  • Speed is reported, not scored.
  • A budget stop never counts as a refusal.
  • The retry is one smaller second pass, taken only if affordable.
  • Misses are published as misses, and each live result is reported only from the build it ran on.

Appendix A

Method made visible

v1: reviewing my own build adversarially

Before shipping v1 I reviewed the build against its own spec across three lenses: does it match the specification, does it use the platform correctly, and what breaks. A separate pass tried to refute every finding. Thirty five claims, thirty one confirmed. The ones that mattered were an intermittent failure on exactly the search heavy cases the product exists for, output budgets that would have cut a brief off mid sentence, a bug that corrupted citations when reassembling the response, and a script injection hole in the shared brief, the file handed to a third party.

v2: gates, replay first, and a typed "proceed"

  • The build ran in phases. Replay phases came first, at no cost; live phases ran only after a typed "proceed", with the planned calls and spend printed first.
  • The ledger reserves each call before it is made, against a $5 cap for the whole build.
  • Every library name was checked against the current release before use.
  • Planted bugs test the tests: all 1,105 are caught.
  • Every run record carries a fingerprint of the code that produced it, so each live v2 result on this page traces to its build: the 18 September results to one fixed build, the safety check's ten live lookups to the later build that added it, and its labeled set scores to Jev calls on 30 September under the locked settings and model jev-1.13.0. The whole build spend is the one total that also counts runs on the earlier build that was replaced.
  • The safety check was scored on a labeled set built before any scoring, with its settings locked and its choice rule written before the held out half was scored once.

What I got wrong

  • v1: I pinned a dependency version from memory instead of checking, and the build failed on the first compile.
  • v1: one of my own tests was wrong. I checked the actual behavior in a browser before changing the assertion.
  • v2: the price check once accepted "$12" from a page that said "$129", caught before any live run.

Honest limits of this write up

  • No technician has used either version.
  • The recorded v2 demo replays live runs of 18 September 2026 with no API call. The four v1 briefs linked in Part 3 remain the record of v1.
  • The v2 property records are synthetic. The property, the owner and the commercial detail are genericized; the equipment and the retrieved documentation are real.
  • Cost comparisons with v1 are estimates computed from v1's logged usage, not measurements of v1's bill.
  • The safety step labels came from three model readers, not from people.

Appendix B

Terms used on this page

  • API: a service the code calls over the internet, paid for by use.
  • LangGraph: a library that runs an AI workflow as a graph of steps; each step reads and writes a shared record of the run, and edges decide what runs next.
  • LangChain: a library of building blocks for AI apps: model connectors, tools, and a ready made agent loop.
  • Checkpoint: a saved snapshot of the run, so a run can stop and continue later.
  • Interrupt: a deliberate pause that waits for a person's answer.
  • Middleware: code that wraps every model call or tool call and can check or stop it before it happens.
  • Schema: the exact shape an answer must have: which fields, of which types.
  • Validator: the code that checks each brief against the rules and clears or rejects what fails.
  • Tool calling: the model asking the code to run a tool, here a search or a page fetch, and reading the result.
  • Structured output: the model answers in a fixed, typed form instead of free text.
  • Knowledge graph: facts stored as things and the links between them, each here carrying the exact sentence that supports it.
  • Replay: running the whole pipeline on recorded model replies and search results, at no cost.
  • Ledger: the running record of spend, checked before every paid call.
  • Planted bug: a deliberate small break in the code, used to check that the tests notice it.
  • Token: a word fragment; models are billed per million tokens.
  • Build: a single frozen version of the code, identified by a fingerprint stored in every run record. "The fixed build" is the one every 18 September live v2 result on this page comes from; the safety check's live lookups ran on a later build; "the whole build" spend is the project's total.
  • HVAC: heating, ventilation and air conditioning equipment.
  • Jev: a judgment model from TypeSafe that answers a yes or no question as a probability from 0 to 1; here, whether a step is a safety step.
  • Recall: the share of real safety steps a check flagged.
  • Precision: the share of a check's flags that were real safety steps.
  • Held out half: the half of a labeled set kept aside from every setting choice, so its score is a fair test.
